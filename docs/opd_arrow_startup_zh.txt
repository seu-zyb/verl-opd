导入顺序绕过方案（h004，诊断 job-1871764）

原顺序导入 vLLM 服务、原顺序加载 tokenizer 后导入服务，均 SIGSEGV（-11）。
PyArrow 单独、pandas 单独、torch 后 PyArrow 均通过。
先 PyArrow 再服务、先 torch/PyArrow 再服务、先 PyArrow 再 tokenizer/服务，均通过。
这些结果支持“导入顺序相关的本地扩展冲突”判断，尚不能确定是哪一个动态库或具体 ABI 问题。
没有证据表明本次崩溃由训练 loss、数据或 GPU 显存不足造成；测试尚未进行完整训练。

run_paper_baseline.slurm 与 run_paper_mopd.slurm 默认设置 OPD_ARROW_FIRST=1。
将 scripts/opd/arrow_first 放在该作业的 PYTHONPATH 最前面，Python 启动时 sitecustomize 提前导入 PyArrow。
同时通过 Ray runtime_env.env_vars 显式传递开关与 PYTHONPATH，覆盖 worker 与继承环境的子进程。
预加载失败会终止该 Python 进程；check_environment.py 检查实际生效的 hook 路径。
不修改系统 site-packages，不改 conda 包版本，不影响未使用该脚本的作业。
该专用目录会优先于环境中已有的同名 sitecustomize，适用于当前已诊断的环境。
Python 启动机制：https://docs.python.org/3.12/library/site.html#sitecustomize
Ray 环境变量：https://docs.ray.io/en/latest/ray-observability/user-guides/debug-apps/general-debugging.html

先在服务器提交 baseline 的两步启动验证：
  sbatch scripts/opd/run_paper_baseline.slurm trainer.total_training_steps=2 trainer.val_before_train=False trainer.test_freq=-1 trainer.save_freq=-1
这保留原 batch 和长度，仍可能比较耗时。通过只说明该规模下两步训练成功，不代表长跑稳定。
然后提交正式 baseline：
  sbatch scripts/opd/run_paper_baseline.slurm
运行另一条 rollout 实验时换为 run_paper_mopd.slurm。

显式关闭（仅用于环境已修复或对照诊断）：
  sbatch --export=ALL,OPD_ARROW_FIRST=0 scripts/opd/run_paper_baseline.slurm
不要启用此设置重跑原来的 import-order 诊断，否则所有子进程都会先导入 Arrow，失去原顺序对照。
